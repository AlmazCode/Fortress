# Fortress: переход с Aster на GitHub

Подготовленная папка уже лежит в правильном локальном репозитории Fortress. Она пока не закоммичена и не опубликована на GitHub.

1. Остановить старые попытки Aster в чатах, сохранив их изменения/checkpoints. Не запускать одновременно старый MCP-режим и новый GitHub-режим для тех же задач.
2. Открыть PROMPTS.md и отправить текст №1 главному. Он сначала проверит исходный репозиторий и опубликованные результаты, затем опубликует эту папку через Git.
3. Другие разработчики получают тот же docs/github-plan через Git. Отправить каждому его текст из PROMPTS.md: №2 Frontend, №3 ML/data, №4 rules/infra. Для локальной имитации использовать разные worktree одной копии Git; отдельный сайт-аккаунт и Aster key не нужны.
4. Сначала K у №1; №4 может параллельно выполнять O1. Остальные идут по своим зависимостям. Результат считается общим только после согласованной интеграции проверенного коммита.

Файлы: PLAN.md — все 36 этапов; DEV1…DEV4 — личные задания; plan.json — исходные точные определения; REQUIREMENTS.md — общее ТЗ; status/DEV-N.md — отдельные журналы; STATUS.md — сводка главного.

Переносить весь холст, запускать Aster MCP или вручную создавать 36 Issues для начала не нужно. Если нужна доска, GitHub Projects можно подключить к Issues/PR позже: https://docs.github.com/en/issues/planning-and-tracking-with-projects/learning-about-projects/about-projects

Экспорт не подтверждает свежие статусы задач и не запускает агентов. Новые разрешения на выполнение/push/PR/merge появляются только когда пользователь отправляет соответствующий текст из PROMPTS.md. Старые продуктовые требования, критерии и ограничения остаются в плане. Последняя подтверждённая общая исходная база: 46b7bc941e64fec5649242b8290607c8f7339819; после принятых изменений нужно использовать актуальный общий контракт, а не откатываться на эту базу.
