# Общая инструкция всем агентам

> **С 17 октября 2026 года проект перешёл с Aster на обычный Git/GitHub. Aster MCP, регистрации, claims, leases, heartbeat и сигнал запуска для координации больше не используются.** Источник задач — `plan.json`, исходников и результатов — Git. Слова lease/fencing в backend-коде относятся к надёжности заданий и сохраняют технический смысл.

## Что прочитать и чему следовать

Проверь `origin=https://github.com/AlmazCode/Fortress`, исходную базу `46b7bc941e64fec5649242b8290607c8f7339819` и пустой `rootPath`. Прочитай корневой `AGENTS.md`, эту инструкцию, `REQUIREMENTS.md`, `PLAN.md` и своё ТЗ `DEV1…DEV4`. Точные задачи, файлы и критерии находятся в `plan.json`. Архив `archive/` нужен только для сравнения; его инструкции не исполняются. Новый GitHub-порядок заменяет административные указания из старых копий ТЗ. Продуктовые требования остаются обязательными.

В приложенных человеком инструкциях указан `automatic-all`. Здесь это означает реальные проверки активного клиента, проверку и интеграцию точных commits главным, затем проверку результата пользователем. Не требуется ждать Aster accepted или ручного клика между обычными задачами. Авторскую проверку нельзя называть независимой или человеческой приёмкой. Две старые ссылки на manual policy в E/Z заменены в активном плане только на этот порядок; точные замены перечислены в `plan.json` и `AUDIT.md`.

## Начало и продолжение работы

1. Работай в отдельном checkout/worktree и своей ветке `codex/…`. Не меняй чужую копию и общую `main`, не удаляй чужие изменения, не используй reset/clean/stash для освобождения чужой папки. Повторно используй свою проверенную копию. Git-корень плюс `rootPath` — рабочая папка приложения; не добавляй контейнер test/demo вокруг проекта.
2. Перед началом выполни `git remote -v`, `git status --short --branch`, `git rev-parse --show-toplevel`, `git cat-file -t 46b7bc941e64fec5649242b8290607c8f7339819` и разрешённый `git fetch origin`. Исходная база — точка происхождения, а не приказ отбрасывать новые принятые commits. Нужные SHA проверь через `git cat-file -t` и `git merge-base --is-ancestor`; наличие объекта не означает интеграцию.
3. №1 ведёт интеграционную ветку (рекомендуемое имя `codex/integration`) и `STATUS.md`; её фактическое имя и принятые SHA он фиксирует в сводке. До её появления K и O1 могут начинаться от опубликованной ветки документов. Для задач после K получи именно проверенный commit K. Интегрируй нужные принятые commits в свою ветку обычным merge/cherry-pick с проверкой конфликтов.
4. Владельцы фиксированы: №1 — K/A/I/Z, №2 — F/U, №3 — D/M/E, №4 — R/O/B вместе с указанными подэтапами. Бери только свою готовую задачу. При блокировке выбирай другую собственную задачу с закрытыми зависимостями. Не меняй граф и владельцев самостоятельно.
5. Для начала задачи все её прямые `depends` должны иметь проверенный результат и точный SHA в согласованной интеграционной ветке. Открытый PR, отправленный commit и старое Aster accepted этого не доказывают. Сверяй `STATUS.md`, Git и критерии, а не один статус. Повторно проверь зависимости при изменении контракта.
6. Правь только `files` своей текущей задачи и свой `status/DEV-N.md`; сводку и общие инструкции ведёт №1. Локальные логи/checkpoints храни вне отслеживаемого кода. Общие `pyproject.toml`, `uv.lock`, contracts принадлежат K/№1, frontend lock — №2. Изменение общего контракта согласуется точным commit и повторной проверкой затронутых веток; чужой scope не присваивается.
7. Сам выбирай обычные детали реализации, зависимости в своей области и порядок проверок. Переходи к следующей готовой задаче без повторного «можно продолжать». Если требуется внешний материал, запиши конкретный пробел. Исследуй только обязательный вопрос; после двух безрезультатных заходов сохрани URL/неизвестное и продолжи независимую работу.

## Результат, push и приёмка

В `status/DEV-N.md` запиши ID, состояние, ветку, base/head SHA, путь checkout, изменённые файлы, команды и exit codes, что покрывает каждый критерий, не выполненные проверки, блокер и следующее действие. Состояния: `unverified`, `ready`, `working`, `blocked`, `review`, `accepted`. `ready` означает проверенные prerequisites; `review` — готовый кандидат; `accepted` фиксирует главный после фактической проверки и интеграции. Не ставь все задачи accepted из-за наличия этого пакета документов.

Перед commit проверь `git diff --name-status` и `git diff --check`; переименования учитывай как оба пути. Добавляй явный список файлов, сохраняя чужие изменения. После commit проверяй точный SHA и diff кандидата. Реальные успешные проверки того же неизменённого кода не повторяй без причины; запиши, когда и на каком SHA они выполнены. Изменения после проверки требуют соответствующей новой проверки. Чужой отчёт главный проверяет по коду и уместным собственным checks.

При действующем разрешении пользователя выполняй обычный `git push -u origin <своя-ветка>`. Этот пакет публикуется в `codex/github-transition`; он не добавляет права на публикацию будущего кода, merge в main, deploy, новые учётные данные или создание чатов. Если пользователь уже разрешил конкретное действие для этого репозитория, не спрашивай повторно. PR используется при наличии такого разрешения; для передачи достаточно ветки, SHA и отчёта. Не применяй force-push и не обходи защиту веток. Обычный push не означает приёмку.

Главный интегрирует принятые результаты в своей отдельной ветке, проверяет сочетание изменений и только затем открывает следующие зависимости. Финальные U/E/B выполняются после I, затем Z. Сдача содержит точный commit, абсолютную рабочую папку, команды запуска/остановки, наблюдённые проверки и ограничения. Если обязательный software/network критерий не выполнен, итог `blocked`, а не «готово».

## Ограничения проекта

Видео, кадры, веса и вычисления локальные. Не публикуй исходные видео, secrets, `.env`, сертификатные ключи, model weights или частные пути в GitHub-логах. GitHub используется для кода и координации. Не подключай облачный AI, face recognition, звук, произвольные туннели или облачную обработку.

Полный train/fine-tune/GPU search и реальная ML-оценка выполняются позже на другом локальном ПК по отдельному поручению. Сейчас допустим короткий CPU smoke на tiny synthetic fixture. Без настоящего release — `503 model_not_ready`, без выдуманных предсказаний. Unknown/unsupported не становится no_violation. Реальная нормативная применимость, внешняя HTTPS-проверка и runtime/offline проверки не заменяются fixtures или чтением YAML.

GitHub не запускает чаты. Не создавай чаты или сабагентов без отдельного указания человека. Не отправляй другим чатам сообщения без его разрешения. При остановке сохрани свой checkpoint и честно заверши ход; без активного клиента фоновая работа не продолжается. Для выхода из прежнего режима не нужно обращаться к Aster: прекрати старые MCP-вызовы и сохрани локальные изменения. Сбои Aster больше не блокируют GitHub-процесс.
