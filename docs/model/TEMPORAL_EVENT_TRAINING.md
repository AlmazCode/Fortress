# Обучение действий и временных интервалов

В обучение добавлены подробные операции из существующего датасета и отдельные слабые интервалы сценарных нарушений. Проверены четыре новых малых модели, DINOv2 и локальная VLM. **Прирост точности не получен; рабочий пакет модели не заменён.**

Перепроверен оригинальный `Кейс_ForteBank.docx`: ограничения «одна CNN + один GRU, до12MB» в нём **нет**. Это бюджет прежних исследовательских вариантов, а не требование заказчика. ТЗ разрешает коммерчески применимые открытые предобученные модели при полностью локальной обработке. Поэтому дополнительно проверяются более сильные предобученные признаки и локальная визуально-языковая модель; прежний бюджет не блокирует их.

## Что исправлено в обучении

Раньше подключённый классификатор обучался на вердикте ролика и общих действиях. Подробные операции и `annotations/violations_weak.json` не обучали отдельную локализацию подозрительного фрагмента. Новые этапы используют их как дополнительное supervision с сохранением происхождения и неопределённости.

- 36 development-видео; четыре зарезервированных источника исключены из обучения и выбора. Все42 оригинала сохранены с прежними SHA.
- 12 классов операций, 1261 размеченный момент. Редкие направления передачи объединены в визуально более общий класс; «выдача денег» встречается в одном видео, «подмена денег» — в одном сценарии.
- Кадры вне заданных интервалов операций не объявляются отрицательными. Неопределённые границы исключаются; перекрывающиеся операции делят целевую массу. Явные наблюдения общих действий сопоставляются только по исходным PTS.
- Для риска используются сценарные интерпретации из `violations_weak.json`. В положительных роликах остальное время остаётся unknown; относительный ranking задаёт приоритет размеченному окну без объявления остальных кадров проверенными отрицательными. В отрицательных роликах применяется прежний `user_scenario` verdict policy.
- Нормализация, поддержка классов, обучение и калибровка выполняются внутри тренировочной части. В риск-этапах CNN/GRU представления получены из **точного checkpoint текущего fold**, а не из модели, обученной на всех36 видео.
- Номинал купюры, проверка личности, запирание сейфа и блокировка ОС не превращены в подтверждённые визуальные факты. Нормативный статус остаётся unknown.

## Полученные результаты

Среднее accuracy на прежних четырёх grouped outer folds и трёх seeds42/137/2026. Порог/вариант выбираются по inner folds; финальные артефакты и отрицательные результаты не переписываются.

| Вариант | Средняя accuracy | Решение |
| --- | ---: | --- |
| Действующий uniform GRU-контроль | 71,30% | Сохранён |
| Новая GRU с подробными операциями | 51,85% | Отклонён |
| Линейный декодер операций + ограниченная коррекция вердикта | 67,59% | Отклонён |
| Локализатор риска: исходный GRU + крупные области изображения | 63,89% | Отклонён |
| Локализатор риска: только256 признаков исходного GRU | 66,67% | Отклонён |
| DINOv2 ViT-S/14 + временные признаки + ridge | 63,89% | Отклонён |

У варианта с крупными областями главный пик риска попал во внутреннюю часть слабого интервала после исключения неопределённых границ в13 из23 положительных видео; у варианта только с GRU — в8 из23. Frame F1 на известных слабых целях —50,51% и48,88%. Вне размеченных окон положительных видео истинная полнота разметки неизвестна; эти значения не являются полноценной проверкой event precision или нормативных нарушений.

Повторные эксперименты на тех же development folds — исследование, а не новая независимая приёмка. Цели80%/95% не достигнуты. Машиночитаемые метрики, SHA протоколов/отчётов и число fits: [EVENT_TRAINING_RESULTS.json](EVENT_TRAINING_RESULTS.json).

DINOv2 детерминирован; его63,89% —23 верных из36 outer-предсказаний, а не среднее трёх seeds. Balanced accuracy60,03%, macro F1 60,17%; все три показателя ниже замороженного контроля. Четыре fold accuracy:70,00%,55,56%,66,67%,62,50%.

## Реализация

| Модуль | Назначение |
| --- | --- |
| `ml.temporal_actions` | Подготовка слабых операций; совместное обучение вердикта и действий; grouped CV |
| `ml.temporal_actions_infer` | Автономный исследовательский пакет с одной CNN и одним GRU |
| `ml.operation_decoder` | Небольшой линейный декодер; коррекция на crossfit-прогнозах |
| `ml.operation_crops` | Фиксированные области стола, передачи предметов, сейфа и прибора; CNN ImageNet не меняется |
| `ml.temporal_risk` | Обучение локализации по слабым сценарным интервалам с fold-specific замороженным CNN/GRU |
| `ml.hidden_risk` | Контроль без дополнительных признаков изображения |
| `ml.temporal_risk_infer` | Пакет дополнительной головы с проверкой SHA и отдельными gates для вердикта/локализации |

Крупные области заданы для существующего ракурса. Разметка, имена файлов, ID известных видео и ожидаемые секунды не подаются на вход при обработке нового видео. Веса/данные/кэши остаются вне Git. Бюджет12MB и одна исходная CNN/один GRU сохраняются в риск-пакете; второй GRU не добавлен.

Native backend распознаёт явно настроенный дополнительный пакет. Совместная модель операций, не прошедшая сравнение, отклоняется до анализа. У риск-пакета отдельно проверяются clip metrics и локализация; при отключённых gates гипотезы не попадают в результат как подтверждённые события. Текущая private config продолжает указывать на прежний `control-v1`.

## Воспроизведение

Пути далее — примеры вне репозитория. Для нового эксперимента всегда используйте новый каталог; завершённые результаты защищены от перезаписи. Нужны подготовленные локальные данные прежних этапов и locked CUDA-окружение. Установите `CUBLAS_WORKSPACE_CONFIG=:4096:8` и запускайте из корня репозитория.

```powershell
.venv\Scripts\python.exe -B -m ml.temporal_actions prepare --root D:\FortressData\training-ready --output D:\FortressRuns\operations-new
.venv\Scripts\python.exe -B -m ml.temporal_actions run --output D:\FortressRuns\operations-new

.venv\Scripts\python.exe -B -m ml.operation_crops --parent D:\FortressRuns\operations-new --output D:\FortressRuns\detail-new
.venv\Scripts\python.exe -B -m ml.temporal_risk prepare --inputs D:\FortressRuns\detail-new --output D:\FortressRuns\risk-new
.venv\Scripts\python.exe -B -m ml.temporal_risk run --output D:\FortressRuns\risk-new
```

Для первоначального сравнения требуются сохранённые fold checkpoints из `object-stage-v2` и итоговый reference из `transition-state-stage-v1`. Программа проверяет точные training IDs; недостающий checkpoint не подменяется full-data моделью. При совместной работе с сервисом используйте его общий GPU lock; команды выше сами не управляют работающим API.

Software checks отделены от качества: финальный полный Python-прогон473 tests/29 subtests/exit0 за151,48с; frontend144 tests и build/typecheck/exit0. Реальный MOV проверяется отдельно по PTS, воспроизводимости score и размеру пакета; это функциональная проверка знакомого обучающего видео.

## Локальная визуально-языковая проверка

Официальный [Qwen3-VL-4B-Instruct-GGUF](https://huggingface.co/Qwen/Qwen3-VL-4B-Instruct-GGUF), Apache-2.0, Q4_K_M и FP16 vision projector. Commit модели `1cd86afb9a95c410a6038ab3b40d8b578c892266`; SHA весов `66358cb18bb6b3b1b6675aa412c7a88ef01d228f481184d13668e5201c730a0a`, projector `256f3a43bd4205ffef48d6b92715e1e70b5b0e9aef06522584967513a9985331`. Официальный [llama.cpp](https://github.com/ggml-org/llama.cpp/releases/tag/b11718), Windows CUDA13.4, build11718/commit547208dca. Веса и runtime скачаны и проверены локально, вне Git. Анализ обращается только к127.0.0.1; облачного AI нет.

`ml.vlm_operations` классифицирует действия по целым исходным кадрам. `ml.vlm_benchmark` фиксирует16 равномерно выбранных кадров на каждый из36 development-источников, без имён/ID видео, разметки и ожидаемых секунд в prompt. Схема JSON допускает только заданные классы и индексы реально переданных кадров. Зарезервированные видео не используются. Бюджет изображения в этом probe — максимум512 vision tokens; это не проверка всех конфигураций Qwen и не рекомендация такого разрешения для мелких объектов.

На576 переданных кадрах277 имели известные слабые цели. Совпадение с множеством допустимых целей —22,02%, macro F1 по13 классам —17,87%. Среднее время декодирования/двух запросов для16 кадров —6,643с, максимум10,109с; загрузка модели и полный API/evidence-проход в эти времена не входят. Binary accuracy этим probe не измеряется. Кандидат не подключён; ответ на одном кадре за1,33с не означает достаточного качества. Слабые операционные цели также не являются независимой человеческой разметкой или нормативными фактами.

Протокол `a6e652a84e5f6011449fa403d56bf5c8ee6e9c52ba1d25d61b716089c7951d67`; оригинальные ответы и отчёт сохранены вне Git. Воспроизведение требует заранее запущенный локальный llama-server на127.0.0.1:8011 с указанными весами, `--offline`, контекст16384, один slot, `--image-max-tokens512`, temperature0/seed42. Затем:

```powershell
.venv\Scripts\python.exe -B -m ml.vlm_benchmark --root D:\FortressData\training-ready --output D:\FortressRuns\vlm-new
```

Такой исследовательский сервер не является публичным API Fortress. В основной сервис он не включён.

Дополнительная функциональная проверка с минимумом/максимумом1024 vision tokens и контекстом12288 выполнена на первых трёх development-источниках:10 совпадений из29 известных слабых целей. Это проверка настройки на development, а не общий benchmark или clip accuracy. Новый вариант также не подключён. Оба временных llama-server после проверки остановлены; они не занимают GPU работающего сервиса.

## Более сильные визуальные признаки

[DINOv2 ViT-S/14](https://github.com/facebookresearch/dinov2) — замороженный энкодер21M, Apache-2.0. Код закреплён на commit7764ea0f912e53c92e82eb78a2a1631e92725fc8, официальные веса `dinov2_vits14_pretrain.pth` имеют локальный SHA `b938bf1bc15cd2ec0feacfe3a1bb553fe8ea9ca46a7e1d8d00217f29aef60cd9`. Перед созданием кэша фиксируются SHA всех Python-файлов внешнего энкодера. Загрузка при inference отключена (`pretrained=False`, только локальный state dict).

Два вида исходного изображения392×392, примерно1fps; global token и2×2 patch pools. Внутри train fold выбираются appearance/temporal summary и один из пяти ridge-параметров. Temporal summary сохраняет порядок четырёх четвертей и изменения признаков. Нормализация/readout и пороги никогда не используют outer-метки; отдельная проверка отвергает пересечение семейств между train и validation. Боксы и ожидаемые времена из разметки на вход энкодера не поступают. Новый ракурс не проверялся.

`ml.dino_probe` сохранил неизменяемый кэш36 источников и выполнил outer evaluation, но стандартный FP32 checkpoint writer отклонил float64 коэффициенты readout. Исходный неудачный запуск сохранён. Отдельный `ml.dino_readout` повторяет детерминированную оценку на этом кэше и сохраняет конечные float64 коэффициенты обычным JSON, без ослабления старого loader. Новый протокол/отчёт сохранены отдельно;155 fit calls, ни один дополнительный банковский видеоматериал не используется. Результаты оценки ниже контроля; пакет не экспортируется в сервис.

```powershell
.venv\Scripts\python.exe -B -m ml.dino_probe prepare --root D:\FortressData\training-ready --output D:\FortressRuns\dino-inputs-new --source D:\Models\dinov2-source --weights D:\Models\dinov2_vits14_pretrain.pth
.venv\Scripts\python.exe -B -m ml.dino_readout --parent D:\FortressRuns\dino-inputs-new --output D:\FortressRuns\dino-readout-new
```

Подготовку GPU-признаков необходимо выполнять с общим `runtime/gpu.lock`, когда сервис не анализирует видео. В выполненном DINOv2-запуске этот lock удерживался.

## Что ограничивает следующий прирост

Повторно увеличить число эпох недостаточно: подробные классы редки и частично визуально неоднозначны, границы сценарных интервалов грубые, а большинство нарушений связано с контекстом/порядком действий. В первом MOV исходный кадр всего464×848; содержимое маленькой купюры нельзя считать достоверным только по сценарной подписи.

Следующий обоснованный этап — проверить точные границы и отрицательные примеры на тех же видео для небольшого набора визуально различимых действий, затем обучать предметный recognizer и правила последовательности с отдельной оценкой precision/recall и ложных тревог. Классы с единственным сценарием и визуально неподтверждаемые условия должны сохранять статус недостаточных данных.

В36 development-источниках `cash_substitution` имеет один положительный ролик, `mix_customer_cash`, оставленная сумка, ключ и жидкость возле денег также представлены единичными сценариями. `transaction_not_recorded` имеет три сценария, но отсутствие проводки не устанавливается по одному светящемуся экрану. Передача плоского предмета и тип/номинал этого предмета — разные цели. Подробная операция не превращает сценарную интерпретацию в проверенное визуальное нарушение. Эти ограничения нельзя устранить добавлением ID/ключа известного видео в модель или подбором порога по проверочным ответам.
